# FinConfigCalc 编码规范

本规范用于统一项目代码风格和基本开发约定，以提高项目的可维护性和可扩展性。尚未确定的规则暂不作限制，待项目演进后再补充。

## 1. 技术基线

- Python 版本统一为 Python 3.12。
- 数据处理统一使用 Polars；新增代码不得引入 Pandas DataFrame。
- 参数解析应优先使用明确的类型校验和白名单规则；只有出现稳定、复用的模型需求时，再引入参数建模库。
- 格式化和检查工具使用 Ruff、Pyright、pytest。
- 文件编码统一使用 UTF-8。

当前运行时依赖包括 Polars、openpyxl、Textual、Rich、Loguru 和 Arrow。源码直接导入的运行时包应在 `pyproject.toml` 明确声明；升级或替换依赖时须检查 Excel 文件兼容性及调度表达式兼容性。项目当前不使用 Pandas DataFrame。

## 2. 目录职责

- `utils/`：存放无业务含义、可复用的底层工具。
- `service/`：存放面向调度表的业务处理函数，目前按功能模块组织。
- `ui/`：存放用户界面相关代码。
- `tests/`：存放测试代码。

项目依赖方向为：

```text
ui -> service -> utils
```

- `utils` 不得导入 `service` 或 `ui`。
- `service` 不得导入 `ui`。

当前 UI 从 Excel 调度表读取 `order`、`function`、`params`、`enabled` 和可选的 `comments` 列；`function` 指向 `service` 中的步骤，`params` 使用 JSON 对象。不要将尚未实现的多工作表配置模型、服务门面或模板目录写成现有架构。

## 3. 工具模块命名

`utils` 目录下的文件统一使用以下前缀：

- `io_`：外部交互工具，例如文件、数据库或接口交互。
- `df_`：数据集处理工具，例如过滤、映射、合并和逆透视。
- `tool_`：不属于外部交互或数据集处理的其他通用工具。

补充约定：

- 文件名、函数名和变量名使用 `snake_case`。
- 类名使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE`。
- 布尔变量优先使用 `is_`、`has_`、`can_` 或 `should_` 前缀。
- 文件名应体现具体用途，避免使用 `common.py`、`helper.py`、`misc.py` 等含义模糊的名称。
- 一个工具文件围绕一个明确能力组织，可以包含多个高度相关的函数，不强制一个文件只包含一个函数。

## 4. 函数设计

- 每个函数只承担一个明确职责。
- 公共函数必须完整标注参数类型和返回类型。
- DataFrame 工具默认不修改输入对象，而是返回新的 DataFrame。
- 不使用可变对象作为默认参数。
- 仅供模块内部使用的函数以 `_` 开头。

## 5. Docstring

所有公共函数和类必须编写 Docstring，至少包含以下内容：

- 功能
- 输入数据
- 输出结果

存在副作用、特殊边界或使用限制时，应增加对应说明。
Docstring 应说明函数行为和重要约束，避免编写与代码含义完全重复的无效描述。

## 6. Polars 数据处理规范

- 公共数据处理接口应明确接收 `pl.DataFrame` 或 `pl.LazyFrame`，避免在同一处理流程中随意混用。
- 列名应通过参数或配置传入，避免在函数内部散落硬编码。
- 根据处理需要明确空值、重复值和排序规则。
- 类型转换应明确目标类型和转换方式，避免依赖不稳定的隐式推断。
- 金额等关键数值允许按明确规则处理空值，但不得将非法非空值或非有限数值静默转换为零。
- 函数名称应准确表达数据处理行为。

## 7. 配置和敏感信息

- 账号、密码、Token、Access Key 等关键信息统一记录在项目根目录的 `config.py` 中。
- `config.py` 不纳入 Git 版本管理。
- 代码中通过导入 `config.py` 获取配置，不在其他源码文件中重复填写敏感信息。
- 提交代码前应确认 `config.py` 未进入 Git 暂存区或提交记录。

## 8. 异常和日志

- 对外部输入和配置错误提供包含字段或步骤上下文的可读异常。
- 不吞掉会影响计算结果的转换错误；错误策略应与空值策略分开定义。
- 使用 Loguru 记录处理进度和关键读写信息，不在日志中输出不必要的敏感业务明细。

## 9. 测试命名规范

- 测试文件命名为 `test_<被测试模块>.py`。
- 测试类命名为 `Test<被测试对象>`。
- 测试函数命名为 `test_<被测试行为>`。
- 当同一行为包含多个场景时，可使用 `test_<行为>_<场景>` 命名。

示例：

```text
tests/
    test_df_reshape.py

TestUnpivotDf
test_unpivot_df
test_unpivot_df_with_empty_dataframe
```

## 10. 质量门禁

提交前运行 `pytest`、`ruff check .`、`ruff format --check .` 和 `pyright`。涉及输入转换、分摊或汇总时，应补充正常值、空值和非法值测试。

## 11. 规范维护

- 新增规范前，应确认该规则符合当前项目的实际需要。
- 尚未确定的技术方案不提前写入强制规范。
- 项目结构、工具链或开发方式发生变化时，应同步更新本文档。
- 规范内容与实际代码约定冲突时，应先讨论并明确采用哪一种方式，再更新代码或规范。
